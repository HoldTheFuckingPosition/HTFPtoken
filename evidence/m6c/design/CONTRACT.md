# M6C offline Redeem codec contract

Stage A design under S113/S114. No client implementation or target execution is assigned until exact independent design Review PASS and the supervisor's internal Stage B handoff. REQUIREMENTS.json is the normative exact grammar/catalog; PROFILE.json pins the sole historical identity set; MATRIX.json freezes required actual-case obligations; EXAMPLE.json and VECTORS.json are explicit documentary inputs, never defaults. All documentation and future code are English.

The result is one existing HTFP Redeem instruction descriptor, never a transaction. It contains only a program ID, ordered public account metadata and program-defined data. No fee payer, message, blockhash, nonce, transaction version, signature, signing material, wallet call/seeds, simulation, broadcast, network or native execution exists. It calculates no payout, quote, tax, Q8 split or recommended minimum. An odd positive A is allowed. No M6A quote is imported or silently substituted.

## Request and fixed trust boundary

The future command is `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=clients python3 -B -m htfp_redeem REQUEST.json`. Exactly one explicit local regular-file pathname is accepted. No stdin, default file, argument flag/help mode, URL fetch, output-file mode or environment-selected profile path exists. Invalid arguments, including help probes, produce CLI_USAGE/exit2. Public reusable codec entrypoints must apply the same contract; they do not open caller-selected dependencies or construct execution context.

Open read-only/nonblocking, fstat the opened descriptor before reading, reject a FIFO/device/socket/directory without blocking, and close every descriptor. A symlink resolving to a regular opened target is permitted. Read at most16385 bytes and reject input over16384. Strict UTF-8 without BOM; strict JSON with no duplicate keys, JSON numeric literal or nonfinite constant. Validate Unicode scalars before UTF-8 encoding/traversal: escaped lone surrogates give INVALID_TEXT, not a traceback. A decoded string/key longer than1024 Unicode characters gives INVALID_SHAPE at `$`. Container depth is at most4, with the root container at1. Booleans are distinct from numeric/quantity strings. Unknown fields are rejected at their nearest declared parent without echoing arbitrary keys. All fields are bounded, typed and explicitly listed in REQUIREMENTS.

Root `schema` is exactly `htfp-redeem-request-v1`. `operation` is encode or decode. `profile` absent/null/UNCONFIGURED means PROFILE_UNCONFIGURED, never an implicit historical or public choice. Only the explicit `LOCAL_M3_HISTORICAL_V1` selector is enabled; another string gives UNSUPPORTED_PROFILE. This profile is the existing public synthetic local M3 identity set, not current account state, Testnet, Devnet, a new deployment or cryptographic network isolation. Production remains UNCONFIGURED.

The future packaged `clients/htfp_redeem/PROFILE.json` must be byte-identical to this design's PROFILE.json. Its exact size/SHA256 are in REQUIREMENTS and must be independently compiled into the implementation. Apply the same nonblocking regular-file open/fstat/close discipline and read no more than expected size+1; missing/altered/truncated/extra bytes or a changed embedded source pin give SOURCE_BINDING_ERROR, with no fallback or request-supplied trust override. The profile embodies frozen source hashes and identity constants. The product does not dynamically reread source prose, derive a public deployment or attest current source/public truth. `source_bindings` and `profile_sha256` in every report are fixed rule-version references, even on an error; they are not assertions that trust validation succeeded. ERROR always leaves validation UNASSESSED.

An encode root has exactly schema/operation/profile/intent, with profile optional only to produce the unconfigured failure. Intent requires source, authority, recipient, amount_base_units, minimum_lamports, authorization_route and signers. No leaf default exists. Route is owner, pda or native_multisig. Signers is an explicit ordered list, including `[]` for kind0. A bounded twelve-key list is parseable so the invalid twelve-signer intent receives a precise finding; more than twelve is INVALID_SHAPE. An invalid intent emits no instruction descriptor.

A decode root has exactly schema/operation/profile/descriptor/route_claim, again with profile optionally absent only for unconfigured rejection. The descriptor requires program_id/accounts/data_hex. Each ordered meta is exactly pubkey/is_signer/is_writable, flags actual booleans, at most21 metas at the shape layer. Route_claim must be explicitly present and either a route enum or null. Null is unresolved intent, never inferred from a key, body kind or flag. `data_hex` is lowercase ASCII even-length hexadecimal, at most512 characters. There is no Base64 alternative; decoded data must then be exactly56 bytes.

All supplied public keys are canonical Base58 for exactly32 bytes,32..44 characters, exact re-encoding equality. This establishes no curve membership, private-key possession, account type, derivation or control. Every quantity is a canonical ASCII u64 decimal string: `0` or `[1-9][0-9]*`, at most20 digits and <=18446744073709551615. No sign, spaces, leading zero, exponent, fraction, JSON number, boolean or coercion is accepted. Minimum0 is valid; amount0 is parsed exactly but is an invalid intent. No source balance or actual supply bound is invented.

## Bytes, intent and authorization

The body is header `485446500102`, A:u64LE at6, minimum:u64LE at14, recipient32 at22, kind:u8 at54, supplied_count:u8 at55. Known kinds0/1 only. Kind0 requires body count0. Kind1 count0..11 passes the initial body predicate; exact descriptor accounts are9+count. Unknown header/version/tag/kind, count>11, kind0/count>0, incorrect body length or actual account count is a fixed structural error. These checks are ordered as listed in REQUIREMENTS.

VALID_INITIAL_BODY labels only this bounded low-level parsing. Full `authorize` at lib.rs240 also requires nonempty kind1 suffix and rejects count0 with7000; the encoder refuses that intent, while the decoder retains its nine metas and body with SIGNERS_REQUIRED/exit1. Similarly A0 is losslessly decoded with AMOUNT_ZERO rather than claimed as valid redemption. Missing source balance/owner/supply is UNASSESSED, so an arbitrary syntactically valid A above the *unknown* current balance cannot be classified from these bytes. Payout positivity/minimum satisfaction are also UNASSESSED.

Owner and compatible PDA both encode kind0/count0, requiring authority signer privilege at the HTFP invocation. The route is an explicit declaration, not a fact recoverable from the bytes. For a PDA, privilege may originate in an existing wallet program's authenticated CPI; the codec generates no seeds, wallet call, top-level signer requirement or policy. A decoder with null route keeps authorization_route=null and reports ROUTE_UNRESOLVED/exit1. Even a declared owner/pda route proves no wallet consent.

Native multisig kind1 requires1..11 distinct supplied suffix keys as intent. Count is supplied account count, never configured n, threshold m or a count of humans. Authority itself need not sign. Repeated configured membership slots and the native matching threshold remain runtime questions; no account data are supplied here. A repeated supplied suffix key or authority in its own suffix is nonconformant. Delegate/permanent-delegate-only spending has no invented payout route. A claimed member list or signer flag is never membership, threshold or signature proof.

## Ordered accounts, aliases and minimum privileges

| Index | Role | Required writable | Required signer |
| --- | --- | --- | --- |
| 0 | fixed Config | false | false |
| 1 | fixed Inventory | true | false |
| 2 | fixed Mint | true | false |
| 3 | explicit source | true | false |
| 4 | fixed Reserve | true | false |
| 5 | explicit recipient | true | false |
| 6 | explicit authority | false | true for kind0; false for kind1 |
| 7 | fixed Token-2022 program | false | false |
| 8 | fixed System program | false | false |
| 9+j | supplied signer[j] | false | true |

False is the absence of a required bit, never a forbidden bit. Before testing a role, OR each privilege over every occurrence of the same key in this descriptor. A true flag in an explicitly permitted alias can satisfy another occurrence's minimum. Extra signer/writable flags are preserved and never create proof of authorization. The standalone descriptor cannot assume an extra privilege from an unknown enclosing transaction; its missing-privilege finding concerns only the supplied descriptor, not a new restriction on actual runtime promotions. Canonical encoding emits the per-occurrence role minimums exactly, without sorting, deduplicating or rewriting repeated keys. Decoding preserves every actual occurrence flag and order. `account_requirements` reports index as a decimal string and suffix role as signer[0], signer[1], etc.; required and effective flags are booleans.

External source/recipient/authority/suffix roles cannot equal any of the nine fixed protected keys: H/M/Token-2022/System/Reserve/Config/Inventory/TaxAuthority/Custody. The fixed-role keys/program ID must match the profile. Recipient bytes must equal meta5 exactly. A mismatching decoder preserves both body recipient and meta5 instead of substituting one.

Other external aliases are represented, including source=recipient, source=authority, source=signer, recipient=authority and recipient=signer and their otherwise compatible combinations. Only suffix duplicates and authority-as-suffix are excluded beyond the fixed protection set. Exact runtime owner/native-type/membership constraints still apply and can make an apparently conforming descriptor inexecutable. No blanket duplicate-role rule, recipient signature or System-owned-recipient requirement is added. A non-System/PDA/native-multisig destination can be selected in principle; actual runtime/rent/payment eligibility remains UNASSESSED.

The source's further `protected` tests (account owner==H, owner==sysvar, or executable) need actual account metadata, absent here. They remain explicitly UNASSESSED, as do source native token owner/mint/state/extensions/CPI Guard, exact native multisig classification and wallet invocation. A public key alone cannot discharge them. Redemption has no Custody/Volume/AMM dependency or solvency input in this codec.

## Reports and deterministic validation

REQUIREMENTS freezes all report keys, catalog messages, source arrays, paths and precedence. For specified errors, print exactly one ASCII-safe sorted-key indented JSON report plus LF, <=32768 bytes, with empty stderr and no OS text/input echo. Error report status is ERROR/2, operation=null, profile=UNCONFIGURED, body/descriptor/intent UNASSESSED, descriptor/intent=null and both arrays empty. Input_sha256 hashes exact fully read input bytes even for parser failures; it is null for usage/unreadable/oversized input. Unexpected operational failures must fail visibly, never emit a conformant report.

On normal structurally parsed requests, source/profile integrity has succeeded and error=null. Encode collects all applicable amount/suffix/alias findings, emits no descriptor on invalid intent and marks body/descriptor NOT_PRODUCED. Otherwise it emits one canonical descriptor. Decode retains a structurally valid descriptor even if fixed identities, recipient, privileges or intent are nonconformant. Its intent source/authority are metas3/6, recipient is the body value and suffix keys remain in supplied order; authorization_route is the declared claim only. Every monetary value, supplied count, kind and index is a decimal string; booleans/null retain types.

Sort findings by ASCII `(path,code)`, at most one per pair. Exact paths/source arrays are in finding_paths/catalog. Any nonconformance other than ROUTE_UNRESOLVED yields NONCONFORMANT/1 and intent NONCONFORMANT. Otherwise null route gives UNRESOLVED/1; otherwise CONFORMANT/0. For decode, descriptor is NONCONFORMANT only if a descriptor-layer finding exists; A0/count0 can have a conformant descriptor but invalid intent. The term CONFORMANT means static request/descriptor intent conformance only. Every report keeps the exact fixed assurance map: authorization_verified=false, signatures_verified=false, wallet_policy_verified=false, execution_guaranteed=false; all listed account/runtime/wallet/backing/public/execution assessments UNASSESSED. No input assertion can change those fields.
