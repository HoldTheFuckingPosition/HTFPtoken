## HTTP and exact responses

Use standard `http.server.BaseHTTPRequestHandler` parsing and its default request-line/header limits; no custom HTTP parser or Host/header conformance project. Only GET has an application handler. One response then connection close; no application keepalive/pipelining loop. The normal GET handler rejects request bodies and Transfer-Encoding; Content-Length may be absent or the single literal0. Target must be origin-form ASCII with exact paths, no percent escaping, plus, fragment, backslash or absolute URL. Unknown paths404. Query order may vary, but duplicate/unknown/missing keys and empty values reject. Health/status accept no query; preview requires exactly `amount_base_units` and `minimum_lamports`. Preview query<=128 bytes.

Application limits: target<=1024 bytes, query<=128 bytes, socket read/write timeout2seconds and JSON response<=16384 bytes. No compression or request-body parsing. Successful GETs and application GET rejections have Content-Type application/json; charset=utf-8, exact Content-Length, Cache-Control:no-store and Connection:close. Normal-handler target/query size rejection is414; unsupported body/target/query400. Unsupported methods and malformed request-line/header failures before a GET handler exists follow stdlib rejection behavior, without an exact JSON-envelope guarantee. Timeouts/disconnect attempts remain counted even if no response can be sent. No CORS allowance, stack trace or arbitrary supplied-header echo is added.

Every application JSON body has api_version=`HTFP_READONLY_V1`, mode=`UNCONFIGURED` or `SYNTHETIC_LOCAL_HISTORICAL`, snapshot_id and snapshot_sha256. Those identifiers are null unless snapshot verification succeeds, then exactly `m4b-supervisor-postprocess-24` and its fixed digest. Errors add exactly `error:{code,message}` with a fixed message per code; no on-chain700x error is claimed. Successful bodies have `error:null`.
